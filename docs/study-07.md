# 마음이 챗봇 7회차 학습 기록

## 1. 오늘 구현한 것
- 응답 대기 상태 관리 / 중복 전송 방지 / disabled
- try/catch/finally
- AbortController / 새 대화 시 이전 요청 취소 / chatSessionId
- 오류 복구 / 모바일 점검 / 다크모드 점검 / 캐릭터 크기 조정

## 2. state란?
- state(상태)는 앱이 지금 어떤 상황인지 기억해두는 값이다.
- 같은 버튼을 눌러도 상태에 따라 다르게 동작해야 할 때 쓴다. 예를 들어 답을 기다리는 중이면 보내기를 막고, 아니면 보내게 한다.
- 마음이에서는 isWaiting(기다리는 중인지), chatSessionId(몇 번째 대화인지), messages(지금까지의 대화) 등이 state다.

## 3. isWaiting은 무엇을 저장하는가?
- 지금 마음이의 답을 기다리는 중인지를 true/false로 저장한다.
- 요청을 보내면 true가 되고, 답이 오거나 오류가 나서 요청이 끝나면 false로 돌아간다.
- sendMessage()는 맨 처음에 isWaiting을 확인해서, true면 메시지를 보내지 않는다. 그래서 답이 오기 전에 연타해도 한 번만 전송된다.

## 4. disabled를 쓰는 이유
- isWaiting은 코드 안에서만 막는 것이라 사용자는 지금 기다리는 중인지 알 수 없다.
- 보내기 버튼과 입력창에 disabled를 걸면 버튼이 실제로 눌리지 않고, CSS로 흐리게 보여서 지금은 보낼 수 없다는 것을 화면으로 알려준다.
- 즉 isWaiting은 코드에서 막는 역할, disabled는 화면에서 막고 알려주는 역할이다.

## 5. finally는 언제 실행되는가?
- try가 성공하든, 오류가 나서 catch로 넘어가든, 중간에 return을 하든 마지막에 반드시 실행된다.
- 그래서 잠금 해제처럼 어떤 경우에도 꼭 해야 하는 일을 finally에 넣는 것이다!

## 6. AbortController가 필요한 이유
- fetch로 보낸 요청은 한번 보내면 답이 올 때까지 계속 기다린다. 새 대화를 시작하면 이전 대화의 답은 더 이상 필요 없는데, 그대로 두면 계속 기다리다가 답이 도착해 새 화면에 섞일 수 있다. AbortController를 만들고 fetch에 signal을 연결해두면, abort()로 진행 중인 요청을 중간에 취소할 수 있다. 취소된 요청은 AbortError를 내기 때문에, catch에서 이 오류는 오류 메시지 없이 조용히 넘어가게 처리했다.

## 7. currentController의 역할
- currentController는 지금 진행 중인 요청의 취소 리모컨(controller)을 맡겨두는 보관함이다.
- controller는 요청을 보내는 함수 안에서 만들기 때문에, + 버튼을 눌렀을 때 실행되는 코드에서는 직접 꺼내 쓸 수 없다. 그래서 맨 위에 currentController를 만들어 어디서든 볼 수 있게 했다.
- 요청을 보낼 때 controller를 currentController에 맡겨두고, + 버튼을 누르면 거기서 꺼내 abort()로 요청을 취소한다.
- finally에서는 currentController에 들어 있는 것이 이번 요청의 controller일 때만 잠금을 푼다. 이전 요청이 뒤늦게 끝나면서 지금 진행 중인 요청의 잠금을 대신 풀어버리지 않게 하기 위해서다.


## 8. chatSessionId가 필요한 이유
- 없으면 내가 메시지를 전송하고 답이 오기 전에 새 대화 버튼을 누를 경우, 새 채팅방에 이전 대화의 답이 날아온다. 하지만 chatSessionId를 사용하면 + → 확인을 누를 때마다 chatSessionId 값이 1씩 올라간다. 요청을 보낼 때는 그 순간의 번호를 requestSessionId에 저장해두고, 답이 도착하면 지금의 chatSessionId와 비교한다. 번호가 다르면 이전 대화의 답이므로 화면에 넣지 않고 버린다. 번호가 같으면 지금 대화의 답이므로 정상적으로 보여준다. 

## 9. abort와 chatSessionId를 둘 다 쓰는 이유
- abort는 진행 중인 요청을 끊어서 이전 대화의 답이 아예 오지 않게 한다. chatSessionId는 그래도 답이 도착했을 때, 요청한 대화와 지금 대화의 번호를 비교해서 다르면 버린다. 둘이 같이 쓰는 이유는 만일 abort코드가 오류가 났을 경우를 대비하기 위함이다. 한마디로 이중방어..ㅎㅅㅎ

## 10. 중복 전송 테스트 (방법/결과/수정 후)
- 방법: 아무 글자를 그냥 계속 보냈다.
- 결과: 보낸 만큼 메시지가 연속으로 전송됐고, 말풍선이 나->ai->나 이 순서로 와야하는데 나나나나-> aiaiaiai 이렇게 왔다.(일반적인 챗봇 형식X)
- 수정 후: 메시지가 한 번만 전송됐다. 답이 올 때까지 보내기 버튼과 입력창이 잠겼고, 답이 오면 다시 풀렸다.

## 11. 새 대화 중 이전 응답 테스트 (방법/수정 전/수정 후)
- 방법: 메시지를 보내고 "마음이가 생각 중..."이 떠 있을 때 새 대화(+) 버튼을 눌렀다.
- 수정 전: 새 대화 화면에 "오늘은 어떤 하루였어?" 다음으로, 내 말풍선 없이 이전 질문의 답변이 나타났다.
- 수정 후: 새 대화 화면에는 첫 인사만 남고, 이전 질문의 답변은 나타나지 않았다. 바로 새 메시지를 보낼 수도 있었다.


## 12. 서버 오류 테스트 (상황/화면반응/다시 사용 가능?)
- 서버를 끄면 서버가 연결되지않았다는 메세지가 뜬다, 다시 서버를 키면 다시 정상적으로 대화할 수 있고 본래 기능을 잃지 않았다.

## 13. 모바일 화면 점검 (잘된 점/수정한 점)
- 다행히 여기서는 수정한 점이 없었다. 말풍선도 다 담겼고 프로필도 잘리지않았고, 모든 기능이 다 정상적으로 작동되었다.

## 14. 다크모드 점검 (잘된 점/수정한 점)
- 다크모드를 해도 안했을때와 기능적 차이는 없었디, 단지 프로필에 검은색 비중이 많아, 하얀색 테두리를 다크모드일때만 css로 만들까 고민중이다.

## 15. 캐릭터 크기 비교 (40/44/48px, 최종 선택, 이유)
- 44px로 하기로 결정함. 48로하면 프로필이 너무 커져서 부담스럽다. 40는 생각보다 작고 상단에 달려있는 펭귄이랑 크기가 거의 똑같아서 좀 그렇다, 그리고 눈이 안좋아 질 것 같았다.

## 16. UI와 UX의 차이
- UI는 사용자가 보는 화면 요소(버튼, 색, 글자 크기, 캐릭터 크기 등)이고, UX는 그 화면을 사용하면서 느끼는 전체 경험(편리함, 이해하기 쉬움, 감정 등)이다.
  예를 들어 응답 대기 중에 보내기 버튼을 흐리게 만든 것은 UI 수정이지만, 그 목적은 사용자가 지금 기다리는 중이라는 것을 알고 버튼을 연타하지 않게 하는 UX 개선인 것이다!!!!


## 17. 오늘 발생한 오류 (오류/원인/해결)

- 오류: 방지 코드를 썼는데도 답이 오기 전에 보내기 버튼을 여러 번 누르면 메시지가 그 수만큼 전송됐다.
- 원인: setWaiting() 함수를 만들어만 두고 한 번도 호출하지 않았다. 그래서 isWaiting이 계속 false여서 sendMessage()의 검사를 항상 통과했다.
- 해결: requestAssistantReply() 시작에 setWaiting(true), finally에 setWaiting(false)를 넣었다. finally에 넣어야 서버 오류가 나도 잠금이 풀린다.(왜??????? finally는 성공하든 실패하든 실행가능)

- 오류: 버튼이 잠겨도 화면에서는 흐려지지 않았다.
- 원인: :disabled CSS를 @media 블록 안에 넣어서 넓은 화면에서는 적용되지 않았다. 
- 해결: CSS를 @media 밖으로 옮겼다.

- 오류: 답을 기다리는 중에 새 대화(+)를 누르면, 새 화면에 이전 질문의 답이 내 말풍선 없이 나타났다.
- 원인: requestAssistantReply() 안에서 AbortController를 만들지 않았고, fetch에 signal도 넘기지 않았다. 답이 도착했을 때 대화가 바뀌었는지 확인하는 requestSessionId 검사도 없었다. 게다가 finally에서 정의되지 않은 controller를 써서 오류가 났다.
- 해결: 요청마다 controller를 만들어 currentController에 저장하고, fetch에 signal을 연결했다. 요청할 때의 chatSessionId를 requestSessionId로 기억해두고, 답이 왔을 때 값이 다르면 버리게 했다.

## 18. 오늘 새롭게 이해한 것
- 변수는 만든 위치에 따라 쓸 수 있는 범위가 정해진다. 함수 안에서 만든 controller는 다른 함수에서 쓸 수 없어서, 맨 위에 currentController를 만들어 맡겨두었다.
- finally는 성공하든 실패하든 반드시 실행되기 때문에, 잠금 해제처럼 꼭 되돌려야 하는 일은 finally에 넣어야 한다.
- abort와 chatSessionId처럼 같은 문제를 두 가지 방법으로 막는 이유를 알았다. 하나가 실패해도 다른 하나가 막아주는 이중 장치다. 
- 새 대화를 누를 때마다 chatSessionId 숫자를 1씩 올리고, 요청을 보낼 때의 번호(requestSessionId)와 답이 도착했을 때의 번호(chatSessionId)를 비교해서 다르면 버리는 방식이 신기했다. 숫자 하나만으로 이 답이 지금 대화의 답인지 이전 대화의 답인지 구분할 수 있었다.
- UI는 눈에 보이는 화면이고, UX는 그 화면을 쓰면서 느끼는 경험이다. 버튼을 흐리게 만든 것은 UI 수정이지만, 목적은 사용자가 기다리는 중이라는 걸 알게 하는 UX 개선이었다.
